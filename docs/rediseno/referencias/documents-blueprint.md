# Blueprint: documentos al modelo derivado (control-documental-ai) — diseño de Opus, decisiones aprobadas

Fuente de verdad para los agentes de implementación. No contradecir; si algo no cierra, reportarlo.

## Decisiones tomadas (defaults aprobados)

1. `down_document` (tipos de baja): se exige SOLO a recursos dados de baja (is_active=false). Coincide con la regla aprendida en CLAUDE.md. (La lógica legacy también lo exigía a activos; ahí no hay casos en la base de trabajo: P4=0.)
2. Estado agregado, prioridad: algún faltante o rechazado → INCOMPLETO; si no, algún vencido → VENCIDO; si no COMPLETO; sin requisitos → SIN_REQUISITOS. Presentado y aprobado cuentan como cargados. (Hoy ganaba "con doc vencida" aunque faltaran documentos.)
3. Mensuales: se exige el período corriente en hora argentina (`YYYY-MM`); solo cuentan para el status si son obligatorios. Se normaliza `MM/YYYY` → `YYYY-MM`.
4. Eliminar un documento = borrado físico de las filas que comparten el path (perímetro: empresa) y se registra el evento con el logger de la app.
5. Documentos NO obligatorios rechazados no afectan el status.
6. `archived_at` se deja de escribir; "Ya no aplica" es derivado (documento cuyo tipo hoy no aplica al recurso). Se conserva la columna hasta M2.
7. Multirrecurso: N filas con el mismo `document_path` (sin batchId).
8. `employees.status` / `vehicles.status` quedan como CACHE escrita SOLO por el motor (`refreshDocumentStatus`), en una sola sentencia set-based, sin triggers; job diario de saneamiento.
9. Triggers que se quedan: auditoría `document_employee_changes_trigger` / `document_equipment_changes_trigger`, `update_updated_at_column`, guardas de otros dominios. Se eliminan los 10 triggers de documentos (controlar*alertas*_, document*types_after*_, trg*update_documents*\*).

## Hechos del código que corrigen el brief inicial

- Tipo `special` con `conditions` vacío o NULL → aplica a todos. Con condiciones cargadas pero todos sus ids inválidos → no aplica a nadie (el builder SQL devuelve ''/TRUE y la función hace CONTINUE). `parseDocumentConditions` devuelve [] en ambos: el motor debe distinguirlos.
- Semántica de condiciones: AND entre objetos de condición, OR dentro de los `ids` de cada objeto. Dos objetos con el mismo `property_key` se combinan con AND (NO portar el agrupado por atributo de CDAI).
- Relaciones M:M: `contractor_employee`, `empleado_aptitudes`, `employee_workshop_sectors` (empleados); `contractor_equipment` (equipos). Comparación de ids como texto (hay columnas bigint como province/brand).
- Guarda de baja legacy: `down_document OR is_active` (decisión 1 la corrige a solo bajas).
- Las guardas WHEN de los triggers dejaban atributos sin vigilar → las filas materializadas están desactualizadas por diseño.
- `documents_company.validity` es texto `DD/MM/YYYY`.
- Sin índices en documents_employees / documents_equipment por applies/tipo.
- No hay código en `src` que escriba state 'aprobado'/'rechazado' (vienen de datos legacy).
- Se rompen sin aviso al borrar las pendientes: `deleteDocumentFile` (vuelve la fila a pendiente, document-files.server.ts:92), `approve-pre-employee.server.ts:127` (updateMany sobre la pendiente → 0 filas, perdería documentos del candidato), `loggedUser.ts:105` (isOperativelyActive) y `shared/store/lib/document-buckets.ts:190,194` leen 'pendiente', `fixDocumentTypeConsistency` / `reactivateDocumentType` crean filas vacías, `pending_counts` de get_documents_expiry_summary.
- `other_equipment.status` también es status_type pero no tiene documentos: fuera de alcance.

## Motor puro — `src/features/Documentacion/shared/compliance/` (sin directiva, sin Prisma)

- `dates.ts`: `arToday(now)` (YYYY-MM-DD vía `argentinaDate()` de `@/features/Jobs/lib/dates`), `arCurrentPeriod(now)` (YYYY-MM), `normalizePeriod(raw)` (acepta YYYY-MM y MM/YYYY), `parseValidity(Date|string)` (Date → argentinaDate; texto DD/MM/YYYY se parsea), `daysUntil(day,today)`. Reusar `EXPIRING_SOON_DAYS = 30` de `shared/lib/document-expiry.ts`.
- `applicability.ts`: `resolveTypeScope(type)` → `{kind:'all'}|{kind:'none'}|{kind:'conditions',conditions}`; `typeAppliesTo(type,resource)` verdadero solo si: tipo activo; `applies` coincide; tipo global (companyId null) o de la empresa del recurso; (`resource.isActive` o ... ver decisión 1: si el recurso está de baja solo aplican los `downDocument`; si está activo NO aplican los `downDocument`); el scope lo admite. `resourceMatchesConditions` (se mueve desde `TiposDocumentos/lib/document-conditions.ts`): AND entre objetos, OR dentro de ids, comparación como texto; M:M lee `resource.relations[relationTable]` (string[] de filterColumn). Tipos: `ComplianceType {id, companyId, applies, mandatory, isActive, monthly, hasExpiry, downDocument, isPrivate, multiresource, scope}`, `ComplianceResource {id, companyId, isActive, direct: Record<string,string|null>, relations: Record<string,string[]>}`.
- `evaluation.ts`: `evaluateResource(resource, types, docs, {today, period})` → `{requirements: EvaluatedRequirement[], notApplicable: ComplianceDoc[], status, mandatoryTotal, mandatoryOk}`. `ComplianceDoc {id, typeId, storedState, validityDay, period, path, createdAt}`; solo cuenta como documento si tiene `path` (una fila vacía legacy se ignora). Requisito = tipo aplicable y obligatorio; un tipo no obligatorio solo genera fila si hay documento (`required:false`). Documento relevante: candidatos del tipo (si es mensual, solo los del período corriente normalizado), orden createdAt desc, el primero no rechazado, si no el rechazado más nuevo, si no null. Estado derivado: 'faltante'|'presentado'|'aprobado'|'rechazado'|'vencido': sin documento → faltante; rechazado → rechazado; `hasExpiry && validityDay < today` o storedState='vencido' → vencido (el día del vencimiento todavía vale); si no el estado guardado; fila legacy 'pendiente' con archivo se lee como presentado. "Por vencer" = marca `expiringSoon` (0 ≤ días ≤ 30), no un estado.
- `status.ts`: `toStatusType()`: COMPLETO y SIN_REQUISITOS → 'Completo'; VENCIDO → 'Completo con doc vencida'; INCOMPLETO → 'Incompleto'.
- `server/dataset.server.ts` (server-only): `loadComplianceDataset(db,{companyId,kind,resourceIds?})`, ~5 queries en Promise.all: tipos del perímetro (globales o propios) y de ese `applies`; recursos con select armado desde los `filterColumn` de `EMPLOYEE_CONDITIONS`/`EQUIPMENT_CONDITIONS` (única fuente); una query por pivote con `in: ids` (registro `RELATION_LOADERS`; tabla no registrada → logger.warn y la condición falla cerrada); documentos con archivo, select mínimo. `db` acepta `tx` tipado como `Pick<Prisma.TransactionClient,…>`. Envoltorio `getComplianceRows = cache(...)`.
- `server/document-status.server.ts`: `refreshDocumentStatus(db, kind, ids | {companyId})`: carga dataset, evalúa y escribe UNA sentencia `$executeRaw`: `UPDATE employees e SET status = v.s::status_type FROM unnest($1::uuid[], $2::text[]) v(id,s) WHERE e.id=v.id AND e.status IS DISTINCT FROM v.s::status_type` (idem vehicles). Solo escribe lo que cambia.
- Eventos que la disparan (dentro de la transacción del escritor): subir (1 o multirrecurso), reemplazar, renovar, eliminar; aprobar/rechazar si existe; crear/editar empleado o equipo (siempre ese recurso, sin lista de columnas); baja/alta; cambios en pivotes (clientes, aptitudes, sectores de taller); escritores de `vehicles.condition` (Mantenimiento) y ExternalApi de empleados; aprobar candidato; crear/editar/activar/desactivar/borrar tipo (se refresca la empresa entera de ese tipo de recurso). Job diario `documents-status` (00:10 AR, `runForEachCompany`, bitácora, ruta `/api/jobs/documents-status` como los jobs existentes) que informa `changed`.
