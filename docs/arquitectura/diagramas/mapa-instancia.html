1 · Al contratar el servicio

Qué se clona, qué se crea y qué se comparte

Se clona repo del cliente

  • El código completo: módulos de src/features, páginas y componentes.
  • Dockerfile, compose y Caddyfile.
  • Workflows de CI y deploy (un archivo mínimo que llama a los del base).
  • Esquema Prisma, migraciones y seed.
  • Tests (Vitest, pgTAP, integración) y la carpeta e2e/.
  • Historia de git y el remoto upstream hacia el base.
  • La ficha instance.yml (se genera nueva).

Se crea nuevo por cada cliente

  • La VPS y su proyecto en Dokploy.
  • PostgreSQL con una base vacía (migraciones y seed).
  • El bucket de RustFS y sus carpetas.
  • Secretos y variables propios.
  • Dominio y certificado TLS.
  • Su imagen de contenedor (se construye con los datos del cliente).
  • Primer administrador, jobs y backups.
  • El registro de la instancia para la app móvil.

Se comparte entre todos

  • El repo base y sus tags de versión.
  • El repo móvil y la app genérica de las tiendas.
  • El CI (GitHub Actions) y los workflows reutilizables.
  • Monitoreo central de todas las instancias (opcional).
  • Proyecto de Expo para las notificaciones push (a decidir).

Lo que se clona es solo código y configuración. Los datos de cada cliente nunca salen de su VPS.

4 · Redis y otros servicios

¿Hace falta Redis en cada instancia?

Redis no aparece en el repo de alphataco: no hay dependencia ni código que lo use (las menciones de "redis" en los archivos son de la palabra "rediseño"). Mi recomendación es no incluirlo por defecto y sumarlo como servicio opcional cuando haya un uso concreto.

Dónde aportaría de verdad

  • Límite de intentos de login compartido. Hoy los contadores viven en un Map en la memoria del proceso (login-rate-limit.ts). Con la web y la API en procesos distintos cada uno contaría por su lado, y todo se reinicia al desplegar.
  • Cola de trabajos con reintentos para push y outbox, si el volumen crece.
  • Avisos en vivo entre procesos (por ejemplo, de la API a la web).

Por qué no lo pondría siempre

  • Es un servicio más por cada VPS: hay que desplegarlo, respaldarlo y monitorearlo en N instancias.
  • PostgreSQL resuelve lo mismo con poco esfuerzo: una tabla de intentos para el límite, y el outbox con bloqueo de filas (SKIP LOCKED) como cola.
  • Redis central compartido entre clientes no es buena idea: rompe el aislamiento y es un punto único de falla.

Otros servicios que se pueden sumar a la VPS

  • Uptime Kuma u otro monitor, en un solo lugar para todas las instancias (no uno por cliente).
  • Una herramienta de backups (restic o rclone) que mande la base y el bucket a un almacenamiento externo.
  • Recolección de logs (Loki y Grafana) si los logs de Dokploy dejan de alcanzar.
  • Mailpit solo en desarrollo; en producción se usa un SMTP real.

Redis queda como un perfil opcional del compose (por ejemplo cache), que se prende en las instancias que lo necesiten. El primer motivo realista es el límite de intentos compartido cuando la API pase a ser un proceso aparte.
