Alphataco · arquitectura de despliegue

La base, cada instancia y lo que lleva cada una

Un repo base, un repo y una VPS por cliente, y siempre el mismo conjunto de servicios por instancia. La app móvil viaja por defecto y se puede apagar para un cliente. Las partes que hoy existen en el repo llevan borde sólido; las que hay que construir, borde punteado.

1 · Vista general

Del base a N instancias

Lo único compartido entre clientes es el base, el CI, el registro de imágenes, Dokploy y la app móvil. Datos, base de datos y bucket son de cada instancia.

2 · Anatomía de una instancia

Qué corre en la VPS de cada cliente

Es siempre la misma plantilla de compose. Se basa en los servicios que ya existen (caddy, app, cron, migrate, postgres, storage) y suma la API y el sync.

Aislamiento entre empresas: hoy lo da withCompany() en cada consulta y no hay políticas RLS en las migraciones. Se mantiene como objetivo, y es requisito si el motor de sync lee la base directamente. El WAL del sync necesita límites (max_slot_wal_keep_size) y alertas de disco para no llenar la VPS.

Ficha de instancia

Un solo archivo por cliente que gobierna el compose, las variables y los tests. Es una propuesta de formato.

cliente: acme
base: v1.4.1
dominio: gestion.acme.com
modulos: [operaciones, mantenimiento,
          almacenes, documentacion]
mobile:
  enabled: true     # false: sin api ni sync
  offline: true     # false: solo online
  push: true
vps: { cpu: 4, ram_gb: 8 }
backups: diario

4 · Despliegue

Del cambio a producción, y cómo llega un tag del base

El pipeline reutiliza los workflows que ya tiene el repo (ci.yml, _build-image.yml, deploy.yml, _deploy.yml). Lo que cambia es que los corre cada repo de cliente.

5 · Operación

Decisiones de diseño

  • Copia con historia común, no repo plantilla: un template pierde la historia y rompe cherry-pick y merge-base.
  • Workflows de build y deploy en el base, fijados a @v1, con un caller de ~20 líneas por clon. Ya son workflow_call. Falta verificar el acceso entre repos.
  • Registro de imágenes por instancia en lugar del registro central, que hoy sería un punto único de falla para todas las VPS.
  • Un servicio Compose en Dokploy con perfil mobile, en vez de servicios sueltos.
  • Rollback como workflow con el sha a restaurar, y migraciones solo aditivas.
  • Secretos fuera de la ficha: instance.yml gobierna dominio, imagen, módulos, móvil y backups.

Fallas verificadas que rompen el alta hoy

  • El seed no corre en la imagen de producción: importa permission-catalog.ts y prisma-pg-config.ts y el Dockerfile no los copia (líneas 124-127). Lo verifiqué leyendo, no ejecuté la imagen.
  • Nadie crea los buckets en producción: solo el compose local y los scripts de demo.
  • deploy.yml trae la imagen y el registro escritos a mano, y NEXT_PUBLIC_* son argumentos de build: hace falta una imagen por cliente.
  • El primer admin es un bloque SQL pegado a mano (runbook).
  • Los IDs de permisos se fijan a mano: dos clones que agreguen un módulo cada uno pueden chocar.

Llevar un módulo de una instancia al base o a otra

El módulo viaja como una carpeta autocontenida con un manifiesto que declara sus permisos, navegación, buckets y jobs.

cliente-A                          alphataco-base                      cliente-B
src/features/X/                    │                                   │
  module.ts (permisos, nav,        │                                   │
  buckets, jobs)                   │                                   │
prisma/schema/x.prisma             │                                   │
prisma/migrations/<ts>_x_*         │                                   │
e2e/specs/x                        │                                   │
   │ module.sh export X            │                                   │
   └── X.patch ───────────────────►│ module.sh import X                │
                                   │  git apply --3way                 │
                                   │  + línea en src/modules.ts        │
                                   │  check-types + migrate diff       │
                                   │  PR → main → tag                  │
                                   │────── git fetch upstream ────────►│ cherry-pick o import
                                   │                                   │ migraciones con el mismo
                                   │                                   │ nombre y checksum
  • Cambios que habilitan esto: esquema Prisma en varios archivos (uno por módulo), un manifiesto por módulo con agregadores centrales para permisos, navegación y buckets, e IDs de permisos deterministas (UUIDv5 de módulo:tab) para que no choquen.
  • Fricción que queda: si el módulo modificó código compartido (src/shared, components/ui), el import lo avisa y se integra a mano.
  • Por verificar: que Prisma 7 acepte la carpeta de esquemas con el COPY prisma del Dockerfile.

6 · Antes del primer clon

Lo que hay que fijar ahora

  1. Contexto explícito en los casos de uso (usuario, empresa, permisos). Hoy salen de next/headers.
  2. Cómo se extienden las tablas del núcleo: tablas laterales 1:1 o una columna JSONB, y esquema Prisma en varios archivos.
  3. Propiedad de las funciones y triggers SQL. Un CREATE OR REPLACE FUNCTION del base puede pisar una personalización del cliente sin conflicto de git.
  4. Contrato /api/mobile/v1 congelado. Lo propio de un cliente va en otra ruta o por configuración del servidor.
  5. Cadencia de merge del base y un umbral de distancia del fork que avise en el CI.
  6. El proceso api separado de la web desde el inicio, con la misma imagen y el mismo tag.
  7. Versiones en lockstep: un tag para web, API y worker.
  8. Push: el token de Expo en cada VPS o un relay central.
